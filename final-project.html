二、Design Log（设计迭代时间轴）

周六上午 — 通信裸板验证与引脚排查
09:00 — 搭建最小通信链路

两块 ESP32-C3 上电，烧录 ESP-NOW 基础收发代码。小车端每秒发送模拟传感器数据，遥控器端串口打印接收内容。通信 OK

关键决策：两端统一数据包结构体 ctrl_packet_t / sensor_packet_t，用 memcpy 而非逐字段拷贝，确保二进制兼容。

10:15 — 遭遇 GPIO9 死坑

编译通过但板子行为异常：LED 不受控、随机重启。

发现：ESP32-C3 的 GPIO9 内部连接 SPI Flash 的 CS 引脚。用作普通 GPIO 会与 Flash 访问冲突，导致启动崩溃。

BLOCKER 
// vehicle.ino — 引脚迁移
#define PIN_LED_STATUS      9    →   #define PIN_LED_STATUS      10

// remote_control.ino — 引脚迁移
#define PIN_BTN_MODE        9    →   #define PIN_BTN_MODE        10

解决 将所有 GPIO9 引用迁移到 GPIO10。此后 GPIO9 列入团队禁用引脚清单。

11:30 — ESP-NOW 信道漂移致收包率崩溃

基础通信正常，但偶尔出现"遥控信号超时"。在 onDataRecv 回调中加入收包计数器后，发现收包率仅 ~1 pkt/s（遥控端以 25Hz 发送，应收 ~25 pkt/s）。

诊断过程：

  1. 排除串口打印阻塞 → 无改善
  2. 排除 TFT SPI 干扰 → 无改善
  3. 定位根因：peer.channel = 0 让 WiFi 栈自动选信道，两块板子随机漂移到不同信道
CRITICAL 
// 改前
esp_now_peer_info_t peer = {};
peer.channel = 0;  // 自动 → 不可靠

// 改后
#include <esp_wifi.h>
WiFi.disconnect();
esp_wifi_set_channel(1, WIFI_SECOND_CHAN_NONE);  // 强制锁定信道1
peer.channel = 1;

结果 收包率从 ~1 pkt/s 跃升至 220+ pkt/s，"遥控信号超时"彻底消失。

周六下午 — 舵机死寂 & TFT 显示迷宫
13:30 — 舵机完全不转：LEDC API 在 Core 3.3.8 下失效

通信正常（收包率 220+），控制指令非零，串口输出的脉宽计算值正确（1000-2000μs），但舵机纹丝不动。

诊断：用 LED+220Ω 电阻测试 GPIO 输出引脚，LED 不亮 → 确认 GPIO 实际无 PWM 波形输出。

根因：ESP32 Arduino Core 3.3.8 下 ledcAttach(pin, freq, res) + ledcWrite(pin, duty) API 不产出实际波形，疑似库版本内部通道分配兼容问题。

BLOCKER 
// 改前 — LEDC API (Core 3.3.8 不工作)
ledcAttach(PIN_DRIVE_SERVO, 50, 16);
ledcWrite(PIN_DRIVE_SERVO, usToDuty(1500));

// 改后 — ESP32Servo 库 (直接操作硬件定时器)
#include <ESP32Servo.h>
Servo driveServo;
driveServo.attach(PIN_DRIVE_SERVO);
driveServo.writeMicroseconds(us);

结果 更换为 ESP32Servo 库后，舵机立即响应。LEDC 方案完全弃用。

附：舵机响应速度分析

收包率 220+ pkt/s 已达 ESP-NOW 代码极限（实测 CPU 空闲率仍有余量，瓶颈在 WiFi 栈调度而非应用层）。MG90S 360° 舵机机械响应时间 50~100ms，是真正的物理瓶颈——电信号再快，齿轮组也跟不上。主 loop 的 delay(5) 已优化为 delay(1)，控制包发送频率设定在 50Hz（每 20ms），在响应速度与 CPU 负载之间取得平衡。

18:30 — 屏幕闪烁：全屏擦除 → 局部刷新技术

每次数据更新调用 tft.fillScreen(BLACK) 全屏擦除，产生明显闪烁。

方案：分离静态标签与动态数据。标签在 page_dirty 时画一次，数据更新时只精准清除数值区域。

// 改前 — 全屏擦除，闪烁明显
void drawDistPage() {
  tft.fillScreen(ST7735_BLACK);     // 全屏闪
  tft.setCursor(0, 10); tft.print("Front:");
  tft.setCursor(30, 10); tft.print(dist);
}

// 改后 — 标签一次，数据精准清除
void drawDistPage() {
  // 静态标签: 仅 page_dirty 时绘制
  if (page_dirty[PAGE_DIST]) {
    tft.fillRect(0, RY(1), SW, SH - RY(1), ST7735_BLACK);
    tft.setCursor(0, RY(3)); tft.print("Front:");     // 一次
  }
  // 动态数据: 只清除数值区域
  tft.fillRect(30, RY(3), SW-30, ROW_H, ST7735_BLACK); // 只清数值区
  tft.setCursor(30, RY(3)); tft.print(dist/10.0, 1);
}

结果 闪烁彻底消除，刷新只发生在数值变化区域。

周日早晨 — 舵机响应延迟根因挖掘 & 实车联调
08:00 — 前进慢/后退正常：多因叠加 Bug

遥控推前进时舵机转速慢且有明显延迟，推后退时转速正常。转向舵机也有延迟。

诊断过程：

  1. 加入 DEBUG_TIMING 开关，输出各阶段耗时（μs）
  2. 发现 Dist=65535mm（N/A）时前进正常（前30s），30s 硬件自检后 HC-SR04 启用，Dist 跳变 → 避障触发
  3. 定位到 三个独立问题叠加：

根因 ①：主 loop 阻塞 → FreeRTOS 独立舵机任务

loop() 中舵机更新排在最末尾，前面有三个阻塞源：pulseIn() 阻塞 30ms、GPS while(available) 无界循环、esp_now_send() 占用 WiFi。遥控端以 50Hz 发送，车端实际舵机更新间隔 30-50ms，延迟累积。

// ★ FreeRTOS 独立任务，优先级 2（高于默认 loop_task 优先级 1）
void servoTask(void *pvParameters) {
  TickType_t lastWakeTime = xTaskGetTickCount();
  while (1) {
    int8_t eff_spd = applyObstacleLimit(incoming_ctrl.speed);
    setDriveSpeed(eff_spd);
    setSteering(incoming_ctrl.steering);
    vTaskDelayUntil(&lastWakeTime, pdMS_TO_TICKS(20));  // 精确 50Hz
  }
}
// setup() 中:
xTaskCreate(servoTask, "servo", 2048, NULL, 2, &servoTaskHandle);

根因 ②：ESP-NOW 回调与避障的竞态条件

两条路径同时修改 incoming_ctrl.speed，产生 100↔30 高频振荡：ESP-NOW 回调写入 100 → 主 loop 避障覆盖为 30 → 回调再次写入 100 → 循环。前进时舵机在 100% 和 30% 之间抖动。

// ★ 统一限速入口 — 只在写入舵机前最后一刻施加
int8_t applyObstacleLimit(int8_t raw_speed) {
  uint16_t d = outgoing_sensor.distance_mm;
  if (d == 65535) return raw_speed;             // 无数据，不限制
  if (d < DISTANCE_STOP_MM)  return (raw_speed > 0) ? 0 : raw_speed;
  if (d < DISTANCE_ALERT_MM) return (raw_speed > 20) ? 20 : raw_speed;
  return raw_speed;
}
// incoming_ctrl.speed 保持遥控器原始值不变
// 限速在 servoTask 和 onDataRecv 中通过 applyObstacleLimit() 统一施加

根因 ③：HC-SR04 噪声触发误避障 → 中断方式 + 三重防护

pulseIn() 可能捕获 ~5μs 噪声脉冲，整数除法后 distance_mm=0。避障条件 0 < STOP(150) 成立，且只拦截 speed > 0（前进），后退完全不受影响——这解释了前进/后退的不对称性。

// ① ISR 替代 pulseIn() — 消除 30ms 阻塞
void IRAM_ATTR hcsr04EchoISR() {
  uint8_t level = digitalRead(PIN_HCSR04_ECHO);
  if (level == HIGH) {
    if (hcsr04_state == HCSR04_TRIGGERED)
      hcsr04_echo_start = micros();
  } else {
    if (hcsr04_state == HCSR04_TRIGGERED && hcsr04_echo_start > 0) {
      unsigned long dur = micros() - hcsr04_echo_start;
      // ② 脉宽校验: 120us~25000us = 2cm~4.3m, 超出即噪声
      if (dur >= 120 && dur <= 25000) {
        hcsr04_echo_dur = dur;
        hcsr04_echo_ready = true;
      }
    }
    hcsr04_state = HCSR04_IDLE;
  }
}
// ③ 滑动窗口中位数滤波 (5样本) — 单个脉冲噪声被过滤
static uint16_t win[5];
// ... 排序取中位数 ...
outgoing_sensor.distance_mm = s[2];  // 中位数

结果 修改前 Dist 值每秒几十次剧烈跳变（23↔31↔150↔2632mm），修改后读数稳定在合理的聚类值。前进/后退响应对称，转向延迟消除。

11:30 — 实车联调：GPS 引脚反接

GPS 模块户外绿灯闪烁（已定位），但遥控器屏幕经纬度/卫星数始终为零。

诊断：HardwareSerial::begin(baud, config, rxPin, txPin) 的 RX/TX 参数顺序搞反。

// 改前 — RX 和 TX 传反了
#define PIN_GPS_TX  7   // 接 GPS 模块 TX → 应为 ESP32 RX
#define PIN_GPS_RX  8   // 接 GPS 模块 RX → 应为 ESP32 TX
gpsSerial.begin(9600, SERIAL_8N1, PIN_GPS_RX, PIN_GPS_TX);  // ← RX=8, TX=7 反了!

// 改后
gpsSerial.begin(9600, SERIAL_8N1, PIN_GPS_TX, PIN_GPS_RX);  // ← RX=7, TX=8 正确

教训 HardwareSerial::begin() 参数顺序是 (rxPin, txPin)，引脚宏命名容易产生歧义。

四、Reflections — 硬核 Bug 与解决方案

#1 ESP-NOW 信道漂移

症状: 收包率 ~1 pkt/s，频繁断连
根因: peer.channel=0 让两板自动选信道 → 不在同一信道
解决: esp_wifi_set_channel(1) 强制锁定 → 220+ pkt/s

反思：ESP-NOW 的 channel=0"自动"选项在各平台行为不一。WiFi 栈在信道间扫描时收包率剧烈波动。强制性信道锁定是本项目通信链路的第一守则。今后所有 ESP-NOW 项目直接锁定信道，不再相信"自动"。

#2 LEDC PWM 不产出波形

症状: 串口显示脉宽正确，但舵机不转
根因: Arduino Core 3.3.8 下 ledcAttach/ledcWrite 不工作
解决: 更换为 ESP32Servo 库 (硬件定时器直驱)

反思：库版本兼容性是嵌入式开发最隐蔽的坑。代码逻辑全对但硬件无输出 → 一定是抽象层出了问题。LED+电阻测试法是最简诊断工具，10秒确认问题不在代码逻辑而在硬件抽象层。

#3 前进慢/后退正常 (三因叠加)

症状: 前进时舵机抖慢，后退正常
根因: ①loop阻塞 ②竞态条件 ③HC-SR04噪声 → 仅影响前进
解决: FreeRTOS解耦 + 统一限速入口 + 中断+脉宽校验+中值滤波

反思：这是本项目最复杂的 Bug——三个独立问题叠加，每个只影响前进方向。最大的教训是："单向不对称 Bug"几乎总是由方向相关条件触发（避障只拦截 speed>0）。调试时要特别注意那些看起来与问题无关的条件分支。FreeRTOS 独立任务对于消除 loop() 阻塞是终极方案，但代价是引入了竞态风险，必须通过统一写入口来消除。

#4 TFT 彩边偏移 (7次失败)

症状: 画面偏移，四边彩边
根因: ST7735 子型号与 initR+rotation 组合不匹配
解决: 历经7种组合 → GREENTAB + rotation 0

反思：ST7735 有多种子型号（GREEN/BLACK/RED/GREENTAB160x80 等），每种对应不同的显示偏移寄存器初始值。自动轮换测试工具（4 方向 × 3 秒）比手动改代码效率提升 10 倍。自定义 offset 子类方法失败的原因是 setRotation() 内部会重新读取 tabcolor 数组覆盖手动设置——不看库源码就写"修复"是无效的。

#5 GPIO19 (USB D+) 占用

症状: SW2 按键无任何响应
根因: ESP32-C3 原生 USB 占用 GPIO19 (D+)
解决: SW2 迁移到 GPIO10

反思：ESP32-C3 的 GPIO 并非全是"通用"的。GPIO9(Flash CS)、GPIO11(VDD_SPI)、GPIO18/19(USB) 都有特定功能。选引脚前应先查芯片数据手册的 Pin Layout 章节。

#6 U8g2 + ST7735 底层冲突

症状: u8g2.begin() 后 TFT 偏移再次错位
根因: u8g2.begin(tft) 内部重置了 TFT 寄存器
妥协: 放弃中文，全英文 6×8px 字体

反思：两个图形库共用同一个 SPI 外设时，后启动的库会覆盖前者的寄存器配置。合理的解决方案是使用 Adafruit_GFX 的自定义字体或 bitmap 方式显示中文，但 Hackathon 时间有限，英文完全可接受。

#7 GPS 引脚反接

症状: GPS 绿灯闪烁但数据为零
根因: HardwareSerial::begin(rx, tx) 参数传反
解决: 交换 begin() 的两个引脚参数

反思：宏命名 PIN_GPS_TX 的歧义是根源——它指的是 GPS 模块的 TX 还是 ESP32 的 TX？把宏名改为 PIN_GPS_TO_ESP / PIN_ESP_TO_GPS 可永久避免此问题。

#8 供电方案踩坑

症状: 加二极管降压后 ESP32 反复欠压复位
根因: 1N5399 二极管压降 0.8~1.0V
解决: 4×AA 电池直连，利用内阻自然降压至 4.5~5.5V

反思：AA 电池内阻是天然的"软降压"——无需额外的稳压模块。舵机独立供电（不经过 ESP32 板载 LDO）但必须共地。电解电容并在电源入口是缓冲舵机堵转电流的最简方案。

调试原则总结

1. LED+电阻是最小可用测试仪
测 PWM 输出、GPIO 电平，用最廉价的工具做最直接的验证，比示波器更灵活（虽然只能看到"有没有"而非"波形长什么样"）。
2. 一次只改一个变量
改一个参数 → 烧录 → 观察 → 记录。多变量同时改动会让"哪个改动生效了"变得不可追踪。TFT 7 种组合的尝试严格遵循了此原则。
3. 串口即眼睛
关键节点加 Serial.println()，调通后降频。收包计数器、时序监控 DEBUG_TIMING 是本次调试最高效的信息源。
4. 记录成功组合
INITR_GREENTAB + rotation 0、STEER_CENTER_US = 1530、esp_wifi_set_channel(1)——这些"最终答案"一旦确认立即记下，不再反复试错。
5. "单向不对称 Bug"先查条件分支
前进慢后退正常 → 一定有只拦截 speed > 0 的逻辑。追踪所有对 speed 有条件判断的代码路径。这次是避障限速 + HC-SR04 噪声 + 竞态三连击。
6. 不要相信库的"自动"选项
ESP-NOW 的 channel=0"自动"在不同平台行为不一致；ledcAttach"应该"工作但在 3.3.8 下不工作。嵌入式开发中，显式 > 隐式，强制 > 自动。

五、问题分析与后续优化方向

5.1 产品目标应用场景

当前项目作为课程 Hackathon 原型验证了 ESP-NOW 遥控 + 多传感器集成的可行性，但产品化目标场景尚未明确。结合现有传感器组合（气体检测 + 超声波测距 + GPS）与舵机驱动底盘的特点，两个可行方向：

场景 A：火灾现场搜救小车

利用气体传感器检测烟雾/有害气体浓度，超声波避障在废墟中导航，GPS 标记搜救位置。可替代消防员进入高温、有毒、结构不稳的危险区域进行初步侦察。

场景 B：管道气体泄漏巡检小车

针对化工厂、燃气管道等场景，小车沿管道巡检，实时检测可燃/有毒气体泄漏，GPS 记录泄漏点坐标，超声波辅助管道内避障导航。

5.2 气体传感器升级 — MQ-135 的局限与替代方案

问题MQ-135 现状影响
预热时间长需 24-48 小时初次预热才能稳定读数不适用于快速部署场景
选择性差对 NH₃、NOx、酒精、CO₂ 等多种气体均有响应，无法区分无法精确定位泄漏气体种类
模拟输出仅输出模拟电压，需 ADC 读取且无数字校准精度受温湿度影响大，一致性差
灵敏度低对低浓度气体（ppm 级）响应弱早期泄漏无法及时预警
无温湿度补偿读数随环境温湿度漂移，需手动校准户外场景数据可靠性不足

按场景推荐替代方案

应用场景推荐传感器检测目标接口优势
火灾搜救 MQ-2 + MQ-7 组合 烟雾、CO、CH₄ 模拟 / 数字 MQ-2 对烟雾灵敏，MQ-7 专测 CO（火灾主要致死气体）
火灾搜救 BME680 VOC、温湿度、气压 I²C / SPI 单芯片多参数，内置温湿度补偿，数字输出免校准
管道巡检 MQ-4 (CH₄) 天然气/甲烷 模拟 对甲烷灵敏度高，适合燃气管道泄漏检测
管道巡检 SGP30 TVOC、eCO₂ I²C 数字输出、自动基线校准、低功耗，适合电池供电
工业级 MH-Z19C (NDIR) CO₂ UART / PWM 非色散红外原理，精度 ±50ppm，寿命长，无需预热
工业级 ZE03 系列 (电化学) CO、H₂S、O₂ 等 UART / 模拟 电化学原理，分辨率达 0.1ppm，适用于危险气体精确定量

5.3 避障系统优化 — HC-SR04 的局限与改进

问题当前局限实际影响
单一方向仅正前方 1 路 HC-SR04无法检测侧方和后方的障碍物，倒车/转向时易碰撞
盲区15° 锥形波束角，近距离（<2cm）无法测量低矮障碍物和贴墙场景无法检测
干扰敏感40kHz 超声波易受环境噪声、同频干扰多个超声模块同时工作会互相干扰读数
材质限制吸音材料（海绵、布料）回波微弱软性障碍物无法可靠检测
刷新率低单次测量需 ~30ms（pulseIn 阻塞）高速移动时避障响应滞后

优化方案

① 多方向超声波覆盖
增加至 3-5 路 HC-SR04，分别覆盖正前、左前、右前、左侧、右侧。使用分时触发（轮询激活，每路间隔 >50ms 避免串扰），构建 180° 避障感知。
引脚规划：每路 TRIG 独立 GPIO，ECHO 可共用中断引脚（中断中通过 TRIG 状态判断来源）。
② 互补传感器融合
增加 VL53L1X ToF 激光测距模块（I²C，4m 量程，±1mm 精度）补充近距离盲区。ToF 不受材质和颜色影响，与超声波互补：超声波覆盖中长距离粗检，ToF 覆盖近距离精确定距。
③ 中断驱动 + DMA 替代阻塞
当前已用 ISR 替代 pulseIn()。进一步优化：使用 ESP32 RMT（远程控制收发器）硬件模块产生超声脉冲和捕获回波，完全释放 CPU，实现非阻塞多路并行测距。理论上 5 路传感器可在 <10ms 内完成一轮扫描（50Hz 刷新率）。
④ 自适应灵敏度 + 动态阈值
根据移动速度动态调整预警距离：静止时 STOP=150mm，低速时 STOP=300mm，高速时 STOP=500mm。增加急停缓冲预测（根据当前速度推算制动距离，提前触发减速），避免惯性碰撞。

5.4 图像传输与摄像头集成

当前系统仅回传传感器数值（距离、GPS 坐标、空气质量），操作者无法直观看到小车前方环境。在火灾搜救和管道巡检场景中，实时图像是决策关键。

方案硬件分辨率传输方式适用场景
方案 1：ESP32-CAM OV2640 摄像头 + ESP32-CAM 模组 UXGA 1600×1200 WiFi MJPEG 流 成本最低，遥控器端浏览器直接查看视频流
方案 2：独立图传 OV5640 + 5.8G 图传模块 1080p 5.8GHz 模拟图传 低延迟（<50ms），适合 FPV 实时操控
方案 3：4G 远程 SIM7600 4G 模块 + 摄像头 720p 4G LTE → 云端 超视距远程监控，无距离限制

推荐实施方案（方案 1 + ESP-NOW 混合架构）

小车端：ESP32-C3（主控 + ESP-NOW） + 独立 ESP32-CAM（视频）
主控 ESP32-C3 维持现有传感器 + 舵机 + ESP-NOW 通信不变。新增一块 ESP32-CAM 模组独立处理视频——OV2640 采集 → JPEG 压缩 → WiFi AP 模式提供 MJPEG 流。遥控器端通过 WiFi 连接小车热点查看视频，ESP-NOW 继续负责低延迟控制指令传输。两路无线互不干扰（WiFi 信道与 ESP-NOW 信道错开）。

硬件增量成本：ESP32-CAM 模组约 ¥25，OV2640 摄像头约 ¥15，合计约 ¥40。
软件改动：小车端增加 CameraWebServer 示例固件（Arduino 自带），遥控器端 UI 增加视频页面（P5 Video），使用 <img> 标签嵌入 MJPEG 地址。

5.5 传感器数据采集、传输与处理系统

现状：小车端仅通过串口实时打印传感器数值，无持久化存储、无远程上报、无历史数据分析。传感器数据停留在"即时显示即丢弃"阶段。

数据链路设计

小车端传感器 ──ESP-NOW──▶ 遥控器端 ──WiFi/4G──▶ 云端/上位机
                              │
                              ├── TFT 实时显示（已有）
                              ├── 本地 SD 卡存储（待实现）
                              └── 上位机串口转发（待实现）
① 本地存储 — SD 卡数据记录
遥控器端增加 microSD 卡模块（SPI，CS→GPIO3），以 CSV 格式定时写入传感器数据包：
timestamp, distance_mm, air_quality, lat, lng, speed, steering
每次上电新建文件（以时间戳命名），事后可导出到 PC 分析。SD 卡写入通过 FreeRTOS 低优先级任务执行，不阻塞 UI 刷新。
② 远程上报 — MQTT + 云平台
遥控器端 WiFi 连接互联网后，通过 MQTT 协议将传感器数据上报至云平台（如阿里云 IoT、ThingsBoard）：
Topic: vehicle/sensors，JSON payload 每分钟上报一次。云端可配置仪表盘、历史曲线、阈值告警（气体超标自动推送通知）。
③ 上位机可视化 — Python + Serial
遥控器端通过 USB 串口将数据转发到 PC，Python 脚本（pyserial + matplotlib）实时绘制传感器曲线：距离时间序列、气体浓度变化、GPS 轨迹地图。适合调试阶段和实验数据分析，无需部署云平台。
④ 数据处理 — 边缘计算初步
在 ESP32 端增加简单数据处理逻辑：滑动平均滤波（已有）、异常值剔除（超出物理量程的数据丢弃）、气体浓度趋势判断（连续 5 个采样点上升 → 判定为泄漏趋势，主动提升上报频率从 1/min 到 1/s）。避免传输原始噪声数据，降低无线带宽占用。
